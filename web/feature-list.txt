1.1 AUTHENTICATION
--------------------------------------------------------------------------------
Files: src/AuthContext.tsx, src/pages/LoginPage.tsx, LoginCredentialsForm.tsx,
LoginMfaStep.tsx, LoginTypes.ts, LoginBrandPanel.tsx, LoginContactModal.tsx,
ForgotPasswordPage.tsx, ResetPasswordPage.tsx, ResetPasswordHelpers.tsx,
OtpBoxes.tsx, MfaSetupPage.tsx, MfaSetupStepFlow.tsx, MfaSetupWidgets.tsx,
MfaActiveBlock.tsx, src/api/authApi.ts, src/api/axiosInstance.ts.

Login flow (LoginPage.tsx → LoginCredentialsForm.tsx):
  - POST /api/v1/auth/login  body { email, password, totp_code? } via
    authApi.login(). Returns AuthResponse { accessToken, refreshToken,
    tokenType, expiresIn, mfaRequired, mfaSessionToken?, user }.
  - If `mfaRequired` is true, tokens are NOT persisted; UI transitions to
    LoginMfaStep.tsx which collects a 6-digit TOTP code (OtpBoxes.tsx — 6
    individually-boxed digit inputs with auto-advance/paste support) and
    resubmits via AuthContext.loginWithMfa(email, password, totpCode), i.e.
    a second POST /api/v1/auth/login now including totp_code.
  - "Remember this device" toggle on the login form controls where tokens are
    persisted: checked → localStorage (survives browser close), unchecked →
    sessionStorage (cleared on tab/browser close). Implemented via
    setRememberDevice() in axiosInstance.ts (module-level `useSession` flag
    that decides which Storage backs authStore()/otherStore()).
  - On success, AuthContext.login() calls persistAuth() (stores accessToken
    in memory, refreshToken + user cache to the chosen Storage, computes
    session expiry from expiresIn) and fires fireAttendanceCheckIn() — see
    §1.1.5 below.
  - LoginBrandPanel.tsx renders the marketing/branding side panel; LoginContactModal.tsx
    is a "contact us" modal reachable from the login screen.

MFA setup (/settings/mfa → MfaSetupPage.tsx, any authenticated user):
  - MfaSetupStepFlow.tsx drives a 3-step wizard: (1) POST /api/v1/auth/mfa/setup
    (authApi.setupMfa()) → returns { secret, qrCodeUri, manualEntryKey }; QR
    code + manual key shown for authenticator app enrollment. (2) user enters
    the 6-digit code from their app; POST /api/v1/auth/mfa/enable
    { totp_code } (authApi.enableMfa()) → returns { recoveryCodes: string[] }
    which are displayed once for the user to save. (3) confirmation step.
  - MfaActiveBlock.tsx renders the "MFA is already enabled" state with a
    "Disable MFA" action → POST /api/v1/auth/mfa/disable { totpCode }
    (authApi.disableMfa()) — requires re-entering a live TOTP code.
  - MfaSetupWidgets.tsx holds the shared visual building blocks (QR display,
    recovery-code list, step indicator) for the wizard.
  - MfaGate.tsx (src/components/MfaGate.tsx, mounted globally in AppLayout) is
    a nag overlay that appears for any authenticated user whose mfaEnabled is
    false and who isn't already on /settings/mfa. It shows a 15s countdown
    ring before "Later" becomes clickable (dark pattern to slow down dismissal),
    and "Later" snoozes the nag for 1 hour via localStorage key
    `rp-mfa-gate-snoozed-until`. "Enable now" routes to /settings/mfa.

Forgot / reset password:
  - ForgotPasswordPage.tsx → POST /api/v1/auth/forgot-password { email }
    (authApi.forgotPassword()). Always appears to succeed (no user-enumeration
    leak) — server sends an OTP by email regardless of whether the address exists.
  - ResetPasswordPage.tsx (+ ResetPasswordHelpers.tsx) is a 2-step flow:
    (1) POST /api/v1/auth/verify-reset-otp { email, otp } (authApi.verifyResetOtp())
    to check the OTP before showing the new-password form: (2) POST
    /api/v1/auth/reset-password { email, otp, newPassword } (authApi.resetPassword()).
  - Change password (ProfileSettingsPage.tsx → ProfileChangePasswordForm.tsx):
    POST /api/v1/auth/change-password { currentPassword, newPassword }
    (authApi.changePassword()) — for an already-authenticated user.

Token storage & refresh (src/api/axiosInstance.ts):
  - Access token lives ONLY in a module-level in-memory variable (never
    persisted) — cleared on full page reload by design.
  - Refresh token + cached user + user ETag persist to localStorage or
    sessionStorage per the "remember device" choice (see above), under keys
    `recoverpro_refresh_token`, `recoverpro_user`, `recoverpro_user_etag`.
  - Request interceptor attaches `Authorization: Bearer <accessToken>` when
    present.
  - Response interceptor: on 401 with an unretried config, calls
    doRefresh(refreshToken) → POST /api/v1/auth/refresh { refreshToken }
    (raw axios call, bypasses the instance to avoid interceptor recursion),
    deduplicated via a shared `refreshPromise` so concurrent 401s trigger only
    one refresh call; replays the original request with the new token on
    success, else clears all auth storage, broadcasts `session_expired` on a
    BroadcastChannel('recoverpro-auth') (for cross-tab logout), and redirects
    to `/login?reason=session_expired`.
  - Separately, on 429/502/503/504 or network errors, requests are retried
    with exponential backoff (429: up to 3 retries honoring `Retry-After`
    header; 5xx/network: up to 2 retries, 500ms*2^n capped at 10s) unless the
    request opted out via `_noRetry`.
  - Non-401/422 failures that survive retries auto-toast via toastBus.error();
    422 is assumed to be inline form validation and 401 is handled by the
    redirect, so both are suppressed from the toast.
  - AuthContext also runs a **proactive refresh** every 13 minutes
    (PROACTIVE_REFRESH_MS) while authenticated (access token TTL is 15 min)
    via proactiveRefresh(), and re-authenticates on tab focus if the last
    refresh was >12 minutes old (STALE_THRESHOLD_MS), to avoid a 401 cascade
    on a long-dormant tab.
  - On mount, AuthContext restores session from storage: if an in-memory
    access token already exists (just logged in) it rehydrates from cache and
    revalidates via GET /api/v1/auth/me; if not, it attempts a silent
    refresh (8s timeout, `_noRetry: true` so failures fail fast) using the
    stored refresh token, then calls /me. A React-StrictMode dedupe guard
    (`initAuthInFlight`) prevents firing two concurrent /auth/refresh calls
    with the same refresh token (server treats the second as replay and
    revokes the whole session family — a real bug that was fixed this way).
    A hard 10s timeout unblocks the "Restoring session" splash regardless.
  - GET /api/v1/auth/me (authApi.me()) uses conditional GET via
    `If-None-Match` with the cached ETag; a 304 reuses the cached user object
    without re-parsing.

Logout:
  - AuthContext.logout(allDevices?) calls POST /api/v1/auth/logout
    { refreshToken } (single device) or POST /api/v1/auth/logout-all (all
    devices/sessions), then clears all local/session storage regardless of
    whether the server call succeeded.

Idle/session handling:
  - session.ts (src/utils/session.ts) tracks a computed expiry timestamp
    (`session.setExpiresAt`) used by SessionExpiryChip.tsx in the topbar to
    show a countdown / "extend session" affordance that calls
    proactiveRefresh() (wired via AppLayout's `onExtend`).
  - Cross-tab sync: BroadcastChannel `recoverpro-auth` — a `token_refreshed`
    message clears sibling tabs' in-memory access token so they silently
    re-refresh on next call instead of racing; `session_expired` forces all
    open tabs to /login.

1.1.5 Attendance auto-check-in on login:
  - Immediately after a successful login (both direct and post-MFA),
    AuthContext.fireAttendanceCheckIn() attempts to read browser geolocation
    (10s timeout) and calls POST /api/v1/attendance/check-in
    { lat?, lng?, accuracy? } (attendanceApi.checkIn()). Success shows a toast
    with the check-in time in Asia/Kolkata; any failure is swallowed silently
    ("must never block the user"). This is how attendance is recorded — there
    is no separate manual "check in" button visible on this call path (manual
    check-in exists as part of AttendancePage — see §Attendance).

1.2 MULTI-TENANCY
--------------------------------------------------------------------------------
  - RecoverPro is single-tenant-per-organization with one platform-level
    super-tenant (PLATFORM_ADMIN). The organization id is NEVER sent
    explicitly by the frontend for org-scoped endpoints — the backend derives
    `organizationId` from the JWT on every request (documented explicitly in
    comments in allocationsApi.ts's `getAllocations`, organizationsApi.ts, and
    dailyDispatchApi.ts: "Tenant id is derived from the caller's JWT on the
    server, never sent here").
  - Legacy/back-compat: some endpoints still accept an explicit `orgId`/
    `organizationId` query param (assignmentsApi.listAssignments,
    collectionsApi.listCollections, reportsApi.*, fieldOpsApi.listActive,
    ptpsApi.listPtps' filterData.organizationId) — these are used by
    PLATFORM_ADMIN-capable call sites or historical code paths; for an
    org-scoped user the param is effectively redundant with the JWT claim.
  - organizationsApi.ts is scoped to "my organization": GET/PATCH
    /api/v1/organizations/me — used by OrganizationSettingsPage.tsx for an
    ORG_ADMIN to view/edit their own org's name (id implicit from JWT).
  - platformApi.ts is the PLATFORM_ADMIN cross-org surface: lists/creates/
    edits/deletes organizations by explicit `{id}` path segment
    (/api/v1/platform/organizations[/{id}]), lists all admin users across
    orgs (/api/v1/platform/users), and reads platform-wide stats/analytics/
    subscriptions/revenue trend. This is the only place the frontend
    operates cross-tenant.
  - There is no org "switcher" widget in the shell for a platform admin to
    "act as" a specific org context for most pages — PlatformSetupPage lets a
    platform admin CRUD organizations and admin users, but day-to-day
    org-scoped pages (Loans, Collections, etc.) are only reachable by an
    org-scoped user's own JWT. (WorkspaceSwitcher.tsx exists in components/
    but is generic tab/workspace UI, not an org switcher — see gaps section.)
  - ActingAsBanner.tsx renders when an "acting as" / impersonation state is
    set (src/utils/impersonation.ts) — a banner reminding the operator they
    are impersonating another account; present in AppLayout's shell globally.

1.3 AUTHORIZATION / RBAC
--------------------------------------------------------------------------------
Role catalog (src/types/core.ts, `Role` union):
  PLATFORM_ADMIN, ORG_ADMIN, MANAGER, TL, FO, CALLER, TRACER
  — plus 3 legacy values kept only so stale JWTs/cached users don't crash the
  UI: FIELD_AGENT, AGENCY_ADMIN, BANK_ADMIN.

Role groups used for route-gating in src/App.tsx:
  - ANY_ORG_ROLE   = [PLATFORM_ADMIN, ORG_ADMIN, MANAGER, TL, FO, CALLER, TRACER]
  - ORG_LEAD_ROLES = [PLATFORM_ADMIN, ORG_ADMIN, MANAGER, TL]
  - ORG_ADMIN_ROLES= [PLATFORM_ADMIN, ORG_ADMIN]
  - PLATFORM_ONLY  = [PLATFORM_ADMIN]

Route gating (src/ProtectedRoute.tsx):
  - Wraps `<Outlet/>` behind `useAuth()`. While `isLoading`, renders a
    full-screen "Restoring session" splash (shared CSS with the boot splash).
  - If not authenticated → `<Navigate to="/login" replace/>`.
  - If `allowedRoles` prop is set, takes `user.roles[0].name` (FIRST role
    only — the app assumes each user has exactly one primary role),  strips a
    leading "ROLE_" prefix, and checks membership in `allowedRoles`. Mismatch
    → renders an inline "Access Denied" panel (not a redirect) with a
    "Back to Dashboard" link.
  - If `allowedPermissions` prop is set (not used in current App.tsx routes,
    but supported), requires `hasAllPermissions(...perms)` from
    `usePermissions()`.
  - Route nesting in App.tsx applies these role-group gates per URL subtree
    (see §1.5 for the concrete route table).

Permission model (src/hooks/usePermissions.ts):
  - Derives a flat, deduped `permissions: string[]` from
    `user.roles.flatMap(r => r.permissions.map(p => p.name))`.
  - Exposes hasPermission, hasAnyPermission, hasAllPermissions, hasRole
    (auto-prefixes "ROLE_" when checking), getAllPermissions, getAllRoles.
  - Permission strings observed in nav gating (src/utils/navConfig.ts):
    DAILY_DISPATCH_CREATE, FILE_UPLOAD, COLUMN_CREATE, ROLE_ASSIGN — nav items
    require BOTH an `alwaysFor` role match AND (if present) all listed
    `permissions`.
  - Role/permission administration UI: RoleManagementPage.tsx (list roles,
    create role, edit a role's permission set) backed by rolesApi.ts
    (GET/POST /api/v1/roles, GET /api/v1/roles/{id}, PATCH
    /api/v1/roles/{id}/permissions, DELETE /api/v1/roles/{id}) and
    permissionsApi.ts (GET /api/v1/permissions — the full permission catalog
    to build the picker). UsersPermissionsModal.tsx additionally grants/
    revokes DIRECT (per-user, outside-role) permissions via
    usersApi.grantPermission/revokePermission
    (POST/DELETE /api/v1/users/{userId}/permissions/{permissionName}).

1.4 API CLIENT
--------------------------------------------------------------------------------
  - Single axios instance: src/api/axiosInstance.ts, `baseURL: ''` (relative —
    frontend and API share an origin/reverse-proxy in production; recorded in
    memory as "must be https://recoverpro.in — raw IP 301-redirects and
    silently breaks all POSTs"), default `timeout: 30_000` ms.
  - All endpoints are versioned under `/api/v1/...`.
  - Response envelope: `ApiResponse<T> = { data: T, message?, success?,
    timestamp?, status? }` — every api/*.ts function unwraps `.data.data`.
  - `PagedResponse<T> = { content: T[], page, size, totalElements,
    totalPages, last }` — Spring-style pagination, used by nearly every list
    endpoint.
  - Idempotency: `newIdempotencyKey()` generates a UUID for money-mutating
    endpoints (collections, deposits) to attach as an `Idempotency-Key`
    header — used at call sites that submit financial transactions.
  - Request-config escape hatches: `_noRetry` (skip backoff retry — used for
    the fast-fail refresh attempt at boot), `_noToast` (skip the automatic
    error toast when the caller wants to handle the error itself).
  - See §1.1 for the full interceptor/refresh/retry/toast behavior.

2.1  /app/dashboard (generic) and /dashboard (fallback) — Dashboard.tsx
--------------------------------------------------------------------------------
File: src/pages/Dashboard.tsx (single monolithic ~1190-line file; the sibling
files DashboardCommon.tsx, DashboardLists.tsx, DashboardOrgView.tsx,
DashboardPlatformView.tsx, DashboardTypes.ts, DashboardUtils.ts, and

Purpose: role-adaptive home dashboard. `/app/dashboard` is actually gated by
`PlatformAdminGuard` in App.tsx: a PLATFORM_ADMIN hitting it is immediately
redirected to `/platform/dashboard` (see §3 below); every other role renders
this component directly. `/dashboard` is a role-agnostic fallback route that
always renders this same component without the platform-admin redirect.

Access: any authenticated user (ANY_ORG_ROLE gate on /app/dashboard; /dashboard
has no role gate at all beyond being authenticated).

Data loading: on mount, fires in parallel:
  - dashboardApi.unified(12) → GET /api/v1/analytics/dashboard?trendMonths=12.
    Returns `UnifiedDashboardData` whose populated sub-sections depend on the
    caller's role/permissions server-side: `platform` (PLATFORM_ADMIN only),
    `orgOverview`, `orgToday`, `collections`, `allocations`, `ptpSummary`,
    `team` (ORG_ADMIN/MANAGER/TL), `callerToday` (CALLER).

    /api/v1/dashboard/field-agent/{agentId} for FO-specific stats
    (todayTotalCases, todayCompletedCases, todayPendingCases,
    todayRescheduledCases, todayCompletionRate, collectedAmountToday,
    pendingPtps).
  - If role is org-level (not FO/CALLER) and role === ORG_ADMIN: a raw
    axiosInstance GET /api/v1/collections?orgId&status=PENDING_APPROVAL&size=100
    for the pending-approvals attention count/amount.
  - For any org-level view: raw GETs to /api/v1/ptps (status=PENDING,
    promisedDateFrom/To = today) for "PTPs due today"; /api/v1/reports/
    visit-completion/daily?orgId for "visits done today"; and
    /api/v1/daily-dispatch/org/summary for "cases dispatched today".
    NOTE: these three calls go straight through axiosInstance rather than a
    named api/*.ts wrapper — an inconsistency vs. the rest of the codebase.

Role-specific views (all client-side branches inside one component):

  - ORG_ADMIN / MANAGER / TL ("org manager view") → KPI band with a

      • Today: Collected today (vs yesterday %), Visits today

      • This month: Outstanding total (click → /app/allocations), Collected
        this month (MoM %, click → /app/collections/trend), Active PTPs

    Below: a multi-line hoverable trend chart (Collections $ area+line, PTPs
    count line, Visits count line) with a 3/6/12-month range toggle, hover

  - CALLER → "Today's Work" KPI band (Cases assigned today → /app/my-cases,
    Calls completed w/ pending sub-metric, PTPs made today → /app/ptps,

  - FO → "Today's Work" KPI band (Today's cases → /app/my-cases, Completed w/

SECTION 18 — OBSERVATIONS & GAPS
================================================================================
Method note: every claim in this document is traced to frontend source
(src/App.tsx, src/pages/*, src/components/*, src/api/*, src/hooks/*,
src/utils/*, src/types/*) actually read during this audit. The backend
(server/src/main/java) was NOT consulted at any point — every behavior
described here is inferred from the frontend/API-contract layer only.
Anywhere the true server-side semantics matter (e.g. exact PATCH
/allocations/{id}/status side effects, exact NotifType trigger conditions,
Stripe webhook handling), treat this doc as the frontend's CONTRACT with the
server, not a guarantee of server behavior — verify against
server/src/main/java before final ops-tool implementation.

18.1  DEAD / UNREACHABLE CODE (built but not wired into routing)
  - FieldOpsPage.tsx + FieldOpsMapPanel.tsx + FieldOpsIncidentPanel.tsx +
    FieldOpsUtils.ts + SosLiveMonitor.tsx (§7.5b): a full-featured SOS/
    incident-monitoring dashboard with live-audio streaming is NOT imported
    by App.tsx anywhere. LiveTrackPage.tsx (routed at /app/live-track) is a
    different, simpler implementation with no incident/SOS panel at all.
    The ops-tool team must decide: rebuild the live-track page WITH the
    orphaned incident/SOS capability (recommended, since it's clearly more
    complete), or treat SOS handling as unimplemented.
  - OrganizationSettingsPage.tsx (§12.5): a complete org name-edit page with
    no route anywhere in App.tsx.
  - Dashboard.css's sibling files DashboardCommon.tsx, DashboardLists.tsx,
    DashboardOrgView.tsx, DashboardPlatformView.tsx, DashboardTypes.ts,
    DashboardUtils.ts, DashboardWidgets.tsx are all 0-byte stubs — Dashboard
    (§2.1) is single monolithic ~1190-line file despite this apparent
    intended split.

18.2  BROKEN / DEAD DEEP LINKS (navigate to a route or query param that has
      no matching handler)
  - UnassignedCasesPage (§4.2): row click → `/app/cases/{id}` — no such
    route; hits the catch-all redirect to /login.
  - TodayVisitsPage (§7.3): row click → `/app/visits/{id}` — no such route
    (only /app/visits and /app/visits/:caseId/submit exist); almost
    certainly meant to append `/submit`.
  - AgentDetailPage (§8.2): "View all" visits link → `/app/visits?agentId=`
    — VisitsPage never reads an `agentId` query param.
  - CollectionMomPage (§5.2): x-axis month click → `/app/collections?month=`
    — CollectionsPage never reads a `month` query param.
  All four land the user on an unfiltered/blank page instead of the
  intended drill-down — worth fixing properly (not just replicating the bug)
  in the ops-tool rebuild.

18.3  DATA INCONSISTENCIES
  - Plan pricing is hardcoded in TWO different places with DIFFERENT
    numbers: subscriptionApi.ts's `PLANS` (Growth ₹2,999/mo, Enterprise
    ₹5,999/mo — used by SubscriptionPage, §14.1) vs. PlatformDashboard.tsx's
    `PLAN_PRICE` map (Starter 2999, Growth 7999, Enterprise 19999 — used
    only to derive the "MRR by plan" chart, §2.2). These are genuinely
    different numbers for the same plans; pick one source of truth for the
    rebuild.
  - DPD (days-past-due) severity banding differs between components:
    LoansPage/MyCasesPage/LoanDetailDrawer use 30/60/90-day thresholds;
    DispatchCasePanel uses 30/90/180-day thresholds for the same concept.

18.4  SYSTEMIC PATTERN — RAW AXIOS VS. WRAPPED API MODULES
  A large fraction of pages call `apiClient`/`axiosInstance` directly with a
  hand-written URL instead of the matching function in `src/api/*.ts` that
  already wraps the identical endpoint (examples: UploadsPage bypasses
  filesApi.listUploads; CollectionsPage/PtpsPage bypass
  collectionsApi.listCollections/ptpsApi.listPtps for their main list
  fetch; LucienPage bypasses lucienApi entirely; MfaSetupPage bypasses
  authApi's mfa methods; AgentsPage/AgentDetailPage/AuditPage/ReportsPage
  all use raw calls for endpoints that have no wrapper, or that duplicate
  one). This is not a functional bug (both paths hit the same URL) but it
  means the `api/*.ts` layer is NOT a reliable single source of truth for
  "every endpoint this app calls" — this document's per-page "Backing APIs"
  lists include the raw-call endpoints precisely because of this. For the
  ops-tool rebuild, treat the per-page endpoint lists in this document (not
  just the api/*.ts files) as the authoritative contract list.

18.5  SEARCH-ONLY-FILTERS-CURRENT-PAGE PATTERN
  Several list pages implement "search" as a CLIENT-SIDE filter over
  whatever page of results is already loaded, not a server-side query
  across the full dataset: CollectionsPage, PtpsPage's KPI-band counts (the
  main PTP list search IS server-side), VisitsPage, UsersPage. Empty-state
  copy on CollectionsPage explicitly warns about this ("Nothing on the
  current page matches..."). LoansPage, UnassignedCasesPage, DailyDispatch's
  panels, and AssignCasePanel do send `searchTerm` to the server correctly.
  Recommend making search consistently server-side in the rebuild.

18.6  RBAC GATING INCONSISTENCY
  Most pages gate actions via `usePermissions().hasPermission(...)`
  (the documented RBAC model, §1.3), but several instead check
  `user.roles[0].name` directly against role strings, sometimes including
  legacy roles that predate the multi-tenant rewrite (AGENCY_ADMIN,
  BANK_ADMIN, FIELD_AGENT — see types/core.ts comment: "to be removed once
  the backend stops emitting them"): UsersPage's canCreate/canDelete,
  OrganizationSettingsPage's canEdit, VisitsPage's canImport,
  CollectionDetailDrawer's canApprove, RoleManagementPage's isPlatformAdmin
  check, UserRequestsPage's canApprove/canSubmit. For the ops-tool rebuild,
  standardize on the permission-string model exclusively and drop the
  legacy role names.

18.7  OTHER NOTABLE GAPS / DEAD FEATURES
  - VisitSubmitPage's "outside calling hours, needs supervisor override"
    validation block is fully built (AfterHoursOverride component,
    validation rule requiring a reason) but `isOutsideHours` is hardcoded to
    `false` in the component — the block can never render or trigger.
  - CaseAssignmentsPage computes per-FO case-count stats by firing one
    allocationsApi.getAllocations call PER FIELD OFFICER in parallel on
    page load — an N+1-style pattern that will not scale gracefully for
    orgs with many FOs.
  - AuditPage merges 4 independently-fetched sources (audit-logs, visits,
    collections, PTPs), each capped at 100 rows with no further pagination
    — busy orgs will silently see only the newest ~100 of each category,
    not a true full history.
  - Several API-layer methods have zero UI call sites anywhere in the app:
    rolesApi.deleteRole, columnSchemasApi.delete (no delete affordance for
    roles or column schemas in their respective admin pages);
    ptpsApi.markBrokenPtps/sendReminders (scheduler-trigger endpoints);
    auditApi's per-entity endpoints (getAssignmentAuditLogs,
    getAllocationAuditLogs, getUserAuditLogs, getAllActionLogs — no
    "view history" link anywhere despite being a natural fit for
    LoanDetailDrawer or UsersPage); subscriptionApi.selectFree (no distinct
    "downgrade to free" action — the Starter plan card routes through the
    same Stripe checkout as paid plans); reportsApi.getFoDay (single-agent
    day report — never surfaced, though MIS EOD's per-FO expandable rows
    cover similar ground); dailyDispatchApi.removeOne (dispatch "undo"
    instead re-POSTs the full remaining case list).
  - Reports (§10.1): only 4 of 11 `ReportType` enum values are exposed in
    the "Generate report" modal (Agent performance, Visit report,
    Collection report, Loan book). TEAM_PERFORMANCE, AGENCY_PERFORMANCE,
    BANK_RECONCILIATION, REASSIGNMENT_FREQUENCY, NPA_IDENTIFICATION,
    MONTHLY_VISIT_COMPLETION have no generate entry point in the UI at all
    (their reportsApi methods for live/on-demand fetch also have no call
    site — see §10.1 unused-methods list). MIS_EOD is served as a LIVE
    dashboard (§10.1a) rather than through the async job queue.
  - Two identically-named `LoginMfaStep.tsx` files exist
    (src/pages/LoginMfaStep.tsx and src/components/LoginMfaStep.tsx);
    LoginPage.tsx imports the pages/ version. Worth a single canonical copy
    in the rebuild.
  - FeatureFlagsPage's per-org scope (§12.6) requires typing a raw
    organization UUID into a text box with no lookup/autocomplete, unlike
    the org-picker dropdowns used elsewhere (UploadsPage, PlatformSubscriptions'
    per-org flag drawer which is reached by clicking an org row instead).
